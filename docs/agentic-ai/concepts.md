# 핵심 개념

> 공식 문서: [Claude API 도구 사용](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) · [Anthropic · Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · [Anthropic · Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

## 1. 에이전트 루프

모든 에이전트의 뼈대는 같습니다.

```text
목표 입력
  └─▶ [모델] 다음 행동 결정 ──▶ 도구 호출이 필요한가?
          ▲                         │ 예                │ 아니오
          │                         ▼                   ▼
          └──── 결과를 대화에 추가 ◀─ [도구 실행]       최종 답변
```

1. 사용자 목표와 사용 가능한 도구 목록을 모델에 보냅니다.
2. 모델이 "이 도구를 이 인자로 호출하겠다"고 응답합니다(`stop_reason: tool_use`).
3. **내 코드가** 도구를 실행하고 결과를 대화에 붙여 다시 보냅니다.
4. 모델이 더 할 일이 없다고 판단하면 최종 답변으로 끝냅니다(`stop_reason: end_turn`).

모델은 도구를 직접 실행하지 않습니다. 실행 권한은 항상 루프를 돌리는 코드(하네스)에 있고, 그래서 **승인·로그·차단을 넣을 자리도 하네스**입니다.

## 2. 구성 요소

| 요소 | 하는 일 | 설계할 때 볼 것 |
| --- | --- | --- |
| 모델 | 판단과 계획 | 작업 난이도에 맞는 모델과 추론 강도(effort) |
| 지침(시스템 프롬프트) | 역할, 목표, 금지 사항 | 규칙 나열보다 이유와 성공 기준을 설명 |
| 도구 | 외부 세계와 상호작용 | 이름·설명·입력 스키마가 곧 사용 설명서 |
| 메모리 | 대화를 넘어 정보 유지 | 무엇을 저장하고 언제 꺼낼지 |
| 하네스 | 루프 실행, 권한, 오류 처리 | 최대 반복 수, 승인 지점, 로그 |
| 환경 | 도구가 실행되는 곳 | 샌드박스, 네트워크·파일 접근 범위 |

## 3. 도구(Tool) 설계

모델은 도구의 **이름, 설명, 입력 스키마**만 보고 언제 어떻게 쓸지 정합니다. 좋은 도구는 사람에게 좋은 API와 비슷합니다.

| 원칙 | 나쁜 예 | 좋은 예 |
| --- | --- | --- |
| 목적 단위로 묶기 | `list_users`, `list_events`, `create_event` 각각 | `schedule_meeting` 하나 |
| 설명에 언제 쓰는지 쓰기 | "파일을 읽음" | "경로를 알 때 파일 전체를 읽는다. 경로를 모르면 먼저 search_files를 쓴다" |
| 결과는 필요한 만큼만 | 원본 JSON 10MB 반환 | 요약 + 다음 페이지 토큰 |
| 오류는 고칠 수 있게 | `Error 500` | "date는 YYYY-MM-DD 형식이어야 합니다. 받은 값: 11/11" |
| 위험한 동작은 분리 | `run_sql`(읽기·쓰기 모두) | `query_readonly`와 승인이 필요한 `execute_write` |

## 4. 컨텍스트 엔지니어링

프롬프트 엔지니어링이 "무엇을 어떻게 물을까"라면, 컨텍스트 엔지니어링은 **긴 작업 동안 모델의 컨텍스트 창에 무엇을 넣고 뺄지 관리하는 일**입니다. 에이전트는 도구 결과가 계속 쌓이므로 이것이 성능을 좌우합니다.

| 기법 | 하는 일 | 언제 쓰나 |
| --- | --- | --- |
| 필요할 때 불러오기 | 전체를 넣지 않고 경로·ID만 주고 도구로 읽게 함 | 큰 코드베이스, 문서 묶음 |
| 컴팩션(요약 압축) | 오래된 대화를 요약으로 대체 | 수십~수백 턴짜리 긴 작업 |
| 도구 결과 정리 | 이미 쓴 오래된 도구 결과를 제거 | 결과가 크고 재사용하지 않을 때 |
| 구조화된 메모 | 진행 상황을 파일(예: `NOTES.md`)에 기록 | 세션이 끊겨도 이어서 해야 할 때 |
| 서브 에이전트 | 탐색을 별도 컨텍스트에서 하고 결론만 받음 | 많이 읽어야 하지만 결론은 짧을 때 |
| 프롬프트 캐싱 | 변하지 않는 앞부분을 캐시 | 같은 지침·도구로 반복 호출할 때 비용·지연 절감 |

## 5. 메모리

| 종류 | 위치 | 예 |
| --- | --- | --- |
| 단기(작업 기억) | 현재 컨텍스트 창 | 지금까지의 대화와 도구 결과 |
| 장기(의미 기억) | 파일, DB, 벡터 저장소 | 사용자 선호, 프로젝트 규칙 |
| 절차 기억 | 지침 파일, 스킬 | `CLAUDE.md`, `AGENTS.md`, 재사용 가능한 작업 절차 |

메모리는 많을수록 좋지 않습니다. 오래되거나 틀린 기억은 엉뚱한 행동을 부릅니다. 저장 기준과 삭제 기준을 함께 정하세요.

## 6. 계획과 추론

최신 모델은 내부 추론(thinking)을 거친 뒤 행동하므로, 예전처럼 "단계별로 생각하라"고 강제할 필요가 줄었습니다. 대신 다음이 효과적입니다.

- **목표와 완료 조건을 처음에 분명히** 준다. ("테스트가 모두 통과하면 끝")
- 긴 작업은 **계획을 파일로 쓰게** 하고 진행할 때마다 갱신하게 한다.
- 추론 강도(effort)를 작업에 맞춘다. 단순 작업에 높은 강도는 비용만 늘린다.

## 7. 멀티 에이전트

한 에이전트가 모든 것을 하면 컨텍스트가 금방 찹니다. 일을 나눠 여러 에이전트가 처리하는 구조가 멀티 에이전트입니다.

| 구조 | 설명 | 장점 | 주의 |
| --- | --- | --- | --- |
| 오케스트레이터–워커 | 리더가 일을 쪼개 워커에 맡기고 결과를 합침 | 병렬 처리, 컨텍스트 분리 | 토큰 사용량이 크게 늘어남 |
| 전문가 핸드오프 | 상황에 맞는 전문 에이전트에게 대화를 넘김 | 역할별 지침이 단순해짐 | 넘길 때 맥락 손실 |
| 에이전트 간 통신(A2A) | 서로 다른 조직·시스템의 에이전트가 표준 규약으로 협업 | 시스템 경계를 넘는 협업 | 신뢰·인증 설계 필요 |

멀티 에이전트는 **병렬로 나눌 수 있고 읽을 양이 많은 일**(리서치, 대량 파일 처리)에서 효과가 크고, 순서가 긴밀하게 얽힌 일(하나의 코드 변경)에서는 오히려 혼란을 늘릴 수 있습니다.

| MCP | 에이전트가 도구·데이터에 연결하는 표준 규약. [MCP 서버 연결](/integrations/mcp) 참고 |

| Guardrail | 입력·출력·행동을 검사해 위험을 막는 장치 |
| Human-in-the-loop | 중요한 행동 전에 사람이 승인하는 구조 |
| Eval | 에이전트 성능을 반복 측정하는 테스트 세트 |
| Skill | 지침·스크립트·자료를 묶어 필요할 때 불러오는 재사용 단위 |
