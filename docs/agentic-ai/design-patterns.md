# 설계 패턴

> 공식 문서: [Anthropic · Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) · [Anthropic · How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) · [OpenAI · A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

가장 중요한 원칙은 **가장 단순한 구조로 시작해서, 측정해 보고 부족할 때만 복잡도를 올리는 것**입니다.

## 패턴 고르기

| 상황 | 추천 패턴 |
| --- | --- |
| 단계가 고정돼 있고 순서대로 처리 | 프롬프트 체이닝 |
| 입력 종류에 따라 처리 방식이 다름 | 라우팅 |
| 서로 독립적인 하위 작업이 여러 개 | 병렬화 |
| 하위 작업 목록을 미리 알 수 없음 | 오케스트레이터–워커 |
| 결과물을 기준에 맞춰 다듬어야 함 | 평가자–최적화 |
| 단계 수도 경로도 예측 불가 | 자율 에이전트 |

## 워크플로 패턴 (코드가 흐름을 정함)

### 프롬프트 체이닝

작업을 순서대로 나누고 앞 단계 출력을 다음 단계 입력으로 넘깁니다. 단계 사이에 코드 검사(게이트)를 넣을 수 있습니다.

```text
초안 작성 ─▶ [검사: 분량·필수 항목] ─▶ 번역 ─▶ 문체 교정
```

- **좋은 곳**: 마케팅 문구 생성 후 번역, 개요 → 본문 작성
- **주의**: 단계를 너무 잘게 나누면 지연과 비용만 늘어남

### 라우팅

입력을 분류해 맞는 처리 경로로 보냅니다. 쉬운 질문은 빠르고 싼 모델로, 어려운 질문은 강한 모델로 보내는 것도 라우팅입니다.

- **좋은 곳**: 고객 문의(환불·기술·일반) 분기
- **주의**: 분류 오류가 전체 품질을 좌우하므로 분류 단계부터 평가

### 병렬화

독립적인 일을 동시에 실행합니다. 두 가지 방식이 있습니다.

| 방식 | 설명 | 예 |
| --- | --- | --- |
| 분할(Sectioning) | 서로 다른 하위 작업을 동시에 | 코드 리뷰를 보안·성능·가독성 관점으로 동시에 |
| 투표(Voting) | 같은 작업을 여러 번 하고 결과를 종합 | 위험 판정을 3회 실행해 다수결 |

### 오케스트레이터–워커

리더 모델이 작업을 쪼개 워커에게 나눠 주고 결과를 합칩니다. 병렬화와 달리 **하위 작업 목록을 실행 중에 결정**합니다.

- **좋은 곳**: 여러 파일에 걸친 코드 변경, 여러 출처를 조사하는 리서치
- **주의**: 워커에게 줄 지시가 모호하면 중복 작업이 생김. 목표·범위·출력 형식을 명확히

### 평가자–최적화

한 모델이 만들고 다른 모델(또는 같은 모델의 다른 역할)이 기준에 따라 평가해 피드백을 주는 반복 구조입니다.

- **좋은 곳**: 번역 품질 다듬기, 검색이 여러 번 필요한 리서치
- **주의**: 평가 기준(루브릭)이 명확하지 않으면 끝없이 돌거나 엉뚱한 방향으로 개선됨. 최대 반복 수를 둘 것

## 에이전트 패턴 (모델이 흐름을 정함)

### ReAct (추론 + 행동)

"생각 → 행동(도구 호출) → 관찰"을 반복하는 가장 기본적인 에이전트 구조입니다. 오늘날 대부분의 도구 사용 에이전트가 이 패턴의 변형이며, 최신 모델 API의 도구 호출 루프가 그대로 이 구조입니다.

### 계획 후 실행 (Plan-and-Execute)

먼저 전체 계획을 세우고, 계획에 따라 실행하며, 막히면 계획을 고칩니다. 긴 작업에서 방향을 잃지 않게 해 주고, 사람이 계획 단계에서 검토할 수 있다는 장점이 있습니다.

### 반성 (Reflection)

결과를 스스로 검토하고 고칩니다. **외부 신호(테스트 결과, 린터, 실행 오류)와 결합할 때** 효과가 크고, 근거 없는 자기 검토는 효과가 제한적입니다.

### 사람 승인 (Human-in-the-loop)

되돌리기 어려운 행동(결제, 배포, 메일 발송, 삭제) 전에는 사람의 승인을 받습니다. 승인 지점은 하네스의 도구 실행 직전에 둡니다.

## 멀티 에이전트 패턴

| 패턴 | 구조 | 대표 사례 |
| --- | --- | --- |
| 리드–서브 에이전트 | 리드가 조사 주제를 나눠 서브 에이전트에 위임 | 리서치 에이전트 |
| 핸드오프 | 대화를 맞는 전문 에이전트에게 넘김 | 고객 상담 분기 |
| 토론·비평 | 여러 에이전트가 서로의 결과를 검토 | 설계 검토, 위험 평가 |
| 파이프라인 | 역할별 에이전트가 순서대로 처리 | 기획 → 구현 → 리뷰 → 테스트 |

멀티 에이전트는 토큰 사용량이 단일 에이전트의 몇 배로 늘어날 수 있습니다. 작업 가치가 그 비용을 정당화하는지 먼저 확인하세요.

## 안티 패턴

| 안티 패턴 | 왜 문제인가 | 대안 |
| --- | --- | --- |
| 처음부터 멀티 에이전트 | 디버깅이 어렵고 비용이 큼 | 단일 에이전트로 먼저 측정 |
| 도구 수십 개를 한꺼번에 | 모델이 도구 선택을 헷갈림 | 목적별로 묶거나 필요할 때 검색해 불러오기 |
| 프레임워크 추상화 뒤에 프롬프트 숨기기 | 실제 무엇이 모델에 가는지 모름 | 최종 요청 내용을 로그로 확인 |
| 종료 조건 없는 루프 | 비용 폭주, 무한 반복 | 최대 반복 수와 예산 설정 |
| 평가 없이 프롬프트 수정 | 개선인지 퇴보인지 모름 | [평가 세트](/agentic-ai/evaluation-safety)부터 만들기 |
